# Evidence and Feedback Lifecycle

See docs/README.md for the full documentation index.*

This is Apex's most distinctive subsystem, and the one most likely to be mischaracterized as "learning" if described loosely. It is not learning. This document is precise on purpose.

## The pipeline

```
CounterfactualDecision
  -> DecisionFollowUpObservation
  -> FollowupEvidenceQualityAssessment
  -> CounterfactualOutcomeAggregate   (versioned aggregate outcome feedback)
  -> Research Operations fact
  -> ResearchAgendaItem
  -> human-reviewed ResearchProposal
```

Every stage is durable, versioned, and replayable. The pipeline ends with a **human**, not a model update.

## 1. Counterfactual decisions

Every retained eligibility decision (`SHARED_OPPORTUNITY_ELIGIBILITY`) or mandate evaluation (`INVESTMENT_MANDATE_EVALUATION`) — regardless of outcome — is normalized into one append-only `CounterfactualDecision` row with a `DecisionDisposition`:

- `ADVANCED` — the underlying decision was favorable (e.g. `ELIGIBLE`, `ALLOWED`)
- `CONSTRAINED` — partially favorable (e.g. `MandateDecisionState.CONSTRAINED`)
- `NOT_ADVANCED` — unfavorable (`REJECTED`, `EXPIRED`, `BLOCKED_MISSING_EVIDENCE`, mandate `REJECTED`)

The original `raw_reason_codes` are preserved verbatim. A separate, versioned `ReasonFamily` classification (see [Opportunity Lifecycle](OPPORTUNITY_LIFECYCLE.md#reason-codes)) interprets those codes without ever mutating the decision itself — two frozen classifier versions (V1, V2) can produce different classifications of the *same* immutable decision.

The ledger's own warning constant states its scope precisely: `"COUNTERFACTUAL DECISION LEDGER — HISTORICAL EVIDENCE ONLY — NO ALLOCATION OR EXECUTION AUTHORITY — NOT A HINDSIGHT STRATEGY-TUNING SIGNAL."`

## 2. Follow-up observations

A `DecisionFollowUpObservation` records **objective, source-attributed market facts** about what happened after a decision — nothing more. Three observation types exist today: `CRYPTO_REFERENCE_PRICE_MOVEMENT`, `KALSHI_MARKET_STATUS_AND_PRICE`, and (added migration `0104`) `SECURITIES_STRUCTURE_TERMINAL_PAYOFF` — the last reuses the existing options-structure payoff function against the underlying's own later-captured reference price, an honest, non-hindsight terminal fact rather than a new evidence source. All three are taken at defined horizons (`SHORT_HORIZON`, `STRATEGY_HORIZON`) from defined baselines (`ORIGIN_EVIDENCE`, `DECISION_TIME`).

The module docstring is unusually direct about what this deliberately excludes, and it's worth quoting exactly:

> *"This module has no vocabulary for `GOOD_REJECTION`/`BAD_REJECTION`/`REGRET`/`SUCCESS`/`FAILURE`/`SHOULD_HAVE_TRADED`/`EDGE`/`VALUE_ADDED` and never will; it stops at objective, source-attributed market facts."*
>
> *"No hypothetical fills, order probability, position sizing, realized P&L, fees not already modeled by the origin decision, slippage, capital reservation, opportunity cost, or alternative-allocation reasoning is computed anywhere in this module."*

A due-state machine tracks each observation's lifecycle: `NOT_YET_DUE` → `DUE` → `OBSERVED`, or `BLOCKED_UNAVAILABLE` / `PERMANENTLY_UNAVAILABLE` / `UNSUPPORTED` if it can never be completed. `NOT_YET_DUE` is normal and expected for recent decisions — it is not a problem to fix.

**Kalshi Settlement & Resolution Evidence Maturation v1 (2026-09-01)** added an authoritative gate in front of `KALSHI_MARKET_STATUS_AND_PRICE`'s own `settlement_result`: it is now only ever a genuine Kalshi provider `result` when the market's own raw `status` is `finalized` — Kalshi's real lifecycle also includes `determined` (a preliminary result, before its dispute window closes), `disputed`, and `amended`, none of which are safe to treat as Apex's knowledge of the market's true outcome. The gate is enforced by a new, dedicated, immutable, content-addressed evidence unit (`domain.kalshi_resolution.KalshiMarketResolutionFact`) that this observation type now reads through rather than trusting the raw provider field directly. See Kalshi Settlement & Resolution Evidence Maturation v1 for the full mechanism, including why this is a distinct evidence unit rather than a widened `DecisionFollowUpObservation` field.

**Counterfactual Forward Outcome Temporal Integrity v1 (2026-09-23, migration `0113`)** added `FOLLOWUP_POLICY_V3` — **CRYPTO only** — and with it the first per-venue policy selection this loop has ever had (CRYPTO → `FOLLOWUP_POLICY_V3`; KALSHI and SECURITIES stay on `FOLLOWUP_POLICY_V2`, because neither venue's follow-up behavior changed and neither is relabelled merely to keep one number across all venues). It corrects two real, already-deployed defects in how a CRYPTO `subsequent_return` was measured:

1. **Pre-anchor movement leaked into a "subsequent" return.** `FOLLOWUP_POLICY_V2` derived its measurement baseline from `completed_utc_day(anchor)`, which *floors* to the start of the anchor's own UTC day — so for any intraday anchor the measured window began *before* the anchor (up to a full calendar day of it). V3 defines the window semantically instead: `W0 = first daily-close boundary at or after the anchor`, `W1 = W0 + horizon_days`. Because `W0 >= anchor` by construction, no pre-anchor movement can enter the number.
2. **The forward endpoint was not replayable.** V2's target lookup applied no availability predicate at all — it took whatever retained batch existed *right now* — and nothing on the row recorded *as of when* it was measured. V3 adds a mandatory, hashed, persisted `measurement_as_of`, declared at sync dispatch, that bounds every endpoint lookup (`batch.completed_at <= measurement_as_of`, applied before a deterministic `(completed_at, observation_id)` ranking). Re-measuring at the same `measurement_as_of` reproduces the identical result forever, even after newer historical batches land; a later `measurement_as_of` may legitimately succeed where an earlier one could not.

V3 also separates two things V2 conflated into one `reference_price_at_baseline`: the **decision-input reference** ("what historical price evidence could Apex *see* at the anchor?" — point-in-time, legitimately stale, retained as disclosure only and **never** an endpoint of `subsequent_return`) and the two **outcome measurement endpoints** (exact nominal buckets under measurement-time availability). Every `FOLLOWUP_POLICY_V1`/`V2` row is untouched, keeps `measurement_as_of IS NULL` permanently (no backfill), and reproduces its `canonical_hash` byte-for-byte; V3 creates parallel corrected evidence through normal versioned lineage, because outcome cohorts already partition on `followup_policy_version`. See Counterfactual Forward Outcome Temporal Integrity v1.

**Counterfactual V2 Research Evidence Quarantine v1 (2026-09-24, no migration)** closes the half of that question the milestone above deliberately did not touch. Stopping CRYPTO from *generating* new V2 evidence did not stop already-retained V2 evidence from being the *source of new research conclusions*: 26 CRYPTO `FOLLOWUP_POLICY_V2` cohorts still held `QUALIFIED`, were still rebuilt every cycle, and 13 of the 26 agenda items they produced still had no proposal and were permanently eligible candidates in every generator run. `domain.counterfactual_followup` now carries a small declarative `(venue, policy_version)` defect table beside the per-venue current-policy selection — `DEFECTIVE_FOLLOWUP_POLICY_VERSIONS` / `followup_policy_version_may_source_new_research` — and `RetainedResearchAgendaSource.facts()` (the single choke point every downstream research surface is fed through) plus `RetainedOutcomeAggregateExperimentExecutor` both honour it. This withdraws **forward sourcing eligibility only**: every retained observation, assessment, aggregate, agenda item, proposal, and feasibility row stays byte-for-byte what it is, V2 CRYPTO aggregates keep being computed and stay fully queryable, and KALSHI and SECURITIES `FOLLOWUP_POLICY_V2` are untouched at every surface. See Counterfactual V2 Research Evidence Quarantine v1.

## 3. Evidence-quality gate

Before any observation is usable downstream, it must pass one centralized, fail-closed gate: `is_evidence_eligible_for_downstream_attribution()`. It returns `ELIGIBLE` or `INELIGIBLE_EVIDENCE`, with defect types `BASELINE_EVIDENCE_INELIGIBLE`, `TARGET_EVIDENCE_INELIGIBLE`, `BOTH_SIDES_EVIDENCE_INELIGIBLE`, `LINEAGE_NOT_RESOLVABLE`, and `OBSERVATION_HASH_INVALID`. Every downstream consumer calls this gate rather than re-implementing its logic — a design choice specifically meant to prevent low-quality evidence from silently leaking into an aggregate.

## 4. Outcome maturation

`CounterfactualOutcomeAggregate` rolls up **cohorts** of decisions (never individual ones) into mean/median/positive-rate return statistics, qualified by `CounterfactualOutcomeQualificationState`: `QUALIFIED`, `INSUFFICIENT_SAMPLE`, or `VENUE_ECONOMIC_REDUCTION_UNAVAILABLE`. As of 2026-08-19, the retained corpus held 104 outcome cohorts and **zero** reached `QUALIFIED` — a dated illustration that this evidence base is still young, not a live guarantee.

The module docstring states the boundary as explicitly as the follow-up module does:

> *"It produces only aggregate evidence over a bounded, explicitly partitioned cohort of decisions — never a per-decision verdict. A sound decision may have a bad stochastic outcome and an unsound decision may get lucky; nothing here ever labels one retained `CounterfactualDecision` 'correct', 'wrong', 'good', or 'bad' from its realized outcome."*
>
> *"It does not tune a strategy, adjust a parameter, mutate a mandate, mutate an allocation, change execution/PAPER/LIVE authority, feed `prioritize()` or any other ranking input, or train anything. Every record this module produces carries `authority = 'NONE'`."*

**Counterfactual Outcome Evidence Specificity v3 (2026-09-26, migration `0114`)** adds `COUNTERFACTUAL_OUTCOME_POLICY_V3` — **CRYPTO only**, beside the frozen V1/V2 — because V1's sample unit (one observation per asset, per decision day, per satisfied reason family, over overlapping windows) is not an independent sample of anything: against the real `FOLLOWUP_POLICY_V3` corpus every CRYPTO `STRATEGY_HORIZON` cohort had "qualified" at +27%..+32% mean raw return with positive rate 1.00 across every method and family — one August rally, not gate-specific evidence. V3 (a) attributes each decision to exactly one reason family by a declared precedence, (b) scores each economic window as the spread between the cohort's products and the **same-method, same-origin products the gate did not reject** (a whole-universe cohort has no complement and is honestly *degenerate*, never a zero-by-construction "sample"), and (c) counts only complete-coverage windows on a fixed-phase grid as independent, qualifying at the unchanged floor of 30 — now counted in windows. Raw returns, complement returns, and the spread over every informative window stay visible as explicitly descriptive fields; the gated statistics carry a sample standard deviation and window span. CRYPTO outcome-policy V1 joins the research-sourcing quarantine (`DEFECTIVE_OUTCOME_POLICY_VERSIONS`), and only `ORIGIN_EVIDENCE` V3 cohorts originate new facts; every retained row, hash, agenda item and proposal is untouched. The read-only production study found 0 V3-qualified cohorts (36 under V1) with 150 of 178 windows degenerate — most gates reject the entire universe each day, so there is no within-method counterfactual yet. See Counterfactual Outcome Evidence Specificity v3.

## 5. Attribution and what happens next

A qualified aggregate becomes a Research Operations fact, which can seed a `ResearchAgendaItem` — something a human researcher can choose to look at. If a person decides the evidence warrants it, **they** write a code or policy change (e.g. adjusting a strategy, tightening an eligibility rule). That change ships through the normal engineering process, same as any other commit.

**Research Proposal Coverage & Fairness v1 (2026-09-21, no migration):** reaching the agenda is necessary but was not previously sufficient for a human to actually see the evidence — `GenerateResearchProposals` (`application/research_operations.py`) turns a bounded number of agenda items into reviewable `ResearchProposal`s each cycle, and two gaps meant SECURITIES structure-outcome facts (and, less severely, KALSHI's own evidence-completion facts) could reach the agenda and then wait there forever, silently, with no error ever raised: (1) `_agenda_template()` had a dedicated, correctly-scored template for `COUNTERFACTUAL_OUTCOME_PATTERN` facts but none for `SECURITIES_STRUCTURE_OUTCOME_PATTERN`, so the latter fell through to the generic `EVIDENCE_COMPLETION` fallback — both a semantic mismatch (that template means "evidence is missing", not "a mature qualified pattern exists") and, empirically, the lowest-scoring proposal class in the system; (2) the generator's priority-sorted, one-per-family selection had no fairness guarantee, so a structurally lower-scoring family could be crowded out of every slot, forever, by a continuously-replenishing higher-scoring one from another venue. Confirmed against production data before the fix: all 6 of SECURITIES' distinct qualified cohorts and all 54 of KALSHI's open agenda items had produced zero proposals, ever, with the oldest waiting since 2026-08-02. Fixed by adding the missing template branch (mirroring `COUNTERFACTUAL_OUTCOME_PATTERN` exactly — still `REPLICATION` class, still `paper_eligible=False`/`live_eligible=False`, still zero automatic approval) and reserving one of the generator's slots per cycle for the single oldest not-yet-proposed candidate whose family didn't otherwise win a slot, guaranteeing bounded progress instead of indefinite starvation. Neither change touches promotion criteria, evidence policy, ranking weights, or authority — see "What feedback does NOT automatically change" below, unchanged by this milestone.

**Research Experiment Executability v1 (2026-09-22, no migration):** Coverage & Fairness v1 above closed the agenda→proposal gap; a direct read-only production audit the same week found the *next* one, immediately downstream: every organically-generated `COUNTERFACTUAL_OUTCOME_POLICY_REVIEW`/`SECURITIES_STRUCTURE_OUTCOME_POLICY_REVIEW` proposal ever produced (13 in production, 0 SECURITIES yet since that fix had not yet naturally fired) landed feasibility `REQUIRES_IMPLEMENTATION`, permanently, because `experiment_engine_compatible` required the proposal's `existing_experiment_id` (a human-readable method id such as `CRYPTO_MULTI_ASSET_REVERSAL_REGIME_V1`) to match an entry in `research_experiment_family` — a structurally separate, SECURITIES-only pre-registration mechanism (`application/research_integrity.py`, "freeze declared research degrees of freedom before execution") that has never registered a single CRYPTO/KALSHI method id and never will; all 11 retained families in production predate this pipeline entirely (2026-07-27/28, `STRATEGY_LAB_CANDIDATE_GENERATION`/`GENUINE_DAILY_DIRECTION_CANDIDATE_EVALUATION`). Only the two 2026-08-03 hand-seeded bootstrap proposals had ever reached review/approval/experiment/recommendation — nothing organic had, in seven weeks, across either venue. Fixed narrowly, for exactly these two families (the only ones whose own `experiment_configuration` already declares a `RETAINED_..._AGGREGATE_ONLY` scope — i.e. they were never meant to need a fresh pre-registered family at all): `GenerateResearchProposals` now also accepts a proposal as engine-compatible when its family matches one of these two, and a new `RetainedOutcomeAggregateExperimentExecutor` (`adapters/research_operations_executor.py`) restates the single already-QUALIFIED aggregate the proposal's own agenda item is anchored to (via `earliest_qualified_per_cohort`, the same deterministic accessor the agenda source itself uses) as a bounded `ResearchExperimentOutcome` — never recomputing, never calling a provider. It honestly reports `liquidity_sufficient=False`/`comparison_improved=False` (a retrospective rollup has no live-position liquidity evidence and no benchmark comparison), so the existing, unmodified `recommend_research_outcome` can only ever reach `REJECT` (the aggregate confirms the current policy) or `REVISE` (the aggregate trends positive; a human should look closer) — never `PAPER_CANDIDATE`, no matter how positive the evidence. Also fixed, for consistency: the `/proposals/{id}/run` console route and the `scripts/dev.py research-operations-queue-execute` CLI command each constructed executor wiring that omitted this dedicated executor (the console route omitted `GovernedResearchExecutor` entirely, bypassing every dedicated executor for anyone calling it directly rather than through the queue) — both now match the console's own queue-execute wiring exactly, so the same proposal reaches the same recommendation regardless of which of the three surfaces an operator uses. Every other `REQUIRES_IMPLEMENTATION` proposal family (`INSUFFICIENT_CALIBRATION`, `FAILED_HEALTH`, `ZERO_SHARED_ELIGIBLE`, `ZERO_PAPER_READY`) is unchanged and deliberately out of scope — none declares a retained-aggregate-only scope, so none has an honest dedicated executor to route to yet. Zero authority change: `paper_authorization_created` stays hardcoded `False` everywhere it is constructed (confirmed by exhaustive grep, no exceptions), and no recommendation of any state has ever applied itself to anything — see the next paragraph.

**Recommendation → governed change remains, by design, a document a human reads, not a workflow that applies itself.** Confirmed by exhaustive grep across the whole codebase: no CLI command and no Operator Console route ever sets `paper_authorization_created=True` or otherwise reads a `ResearchRecommendation` to change a strategy version, threshold, ranking weight, or evidence-eligibility rule. This is the same deliberate boundary already documented above ("a person decides... **they** write a code or policy change") — not a gap this milestone closes, because doing so would mean building an "apply an accepted recommendation" workflow before a single organic recommendation has ever reached `PAPER_CANDIDATE` to design it against. That is the natural next step once this fix has run for real and produced one.

## What feedback currently changes

- Produces durable, queryable, versioned evidence about what happened after a decision.
- Surfaces a candidate item on a human research agenda, and — fairly, across every venue, within a bounded number of cycles — a human-reviewable proposal (see the note directly above).

## What feedback does NOT automatically change

- Does not tune, retrain, or adjust any strategy or model.
- Does not change `prioritize()`'s weights or any other ranking input.
- Does not mutate a mandate or an allocation.
- Does not change execution, PAPER, or LIVE authority.
- Does not label any individual past decision as correct or incorrect.

**Do not describe this as autonomous model retraining or self-improving learning — that is not what the implementation does, and the module docstrings above are explicit and repeated on this exact point.** What Apex has built is a rigorous, replayable evidence-accumulation and human-attribution pipeline — a meaningfully different (and, for a system this cautious about capital authority, more appropriate) capability.
